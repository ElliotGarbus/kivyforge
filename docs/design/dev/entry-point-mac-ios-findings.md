## Defects

None in #68. The new iOS C code compiled and linked on the first build, for
the simulator and for a device, and every check passed, including exit
status 7 on a physical iPhone. Three observations follow. None is specific to
function entry points; the first two are what the prompt asked to have
reported, not judged.

### 1. iOS: an app whose entry code returns stays alive on its last frame

After a tap stopped the app, the console printed `KF-GUI-DEMO: main()
returning`, and the process stayed alive. `simctl launch --console-pty` stayed
attached, `launchctl` still listed the app, and the screen kept its last frame,
with the button frozen in its pressed colour (`ios-after-tap.png`). No crash
report was written.

This is the bootstrap's tail, not the launcher's. When the launcher returns,
`_run_python()` calls `Py_Finalize()` and `_sdl_callback` returns 0, which is
exactly what happens when a bare-form `runpy` run returns. SDL's UIKit
lifecycle then keeps the app running. Whether an app that ends itself should
instead leave the process (as desktop does), or whether iOS apps should
simply never stop, is a separate decision. The usual iOS answer is that an app
does not quit itself.

The phone does the same (Step 6): after the tap, `main() returning`, and the
app stayed on its last frame with the button in its pressed colour; further
taps did nothing.

### 2. iOS simulator: `simctl` does not report the app's exit status

On the simulator, the non-zero path (`SystemExit(7)` through `PyErr_Print`)
ran, the probe was written, and the process ended, but `simctl launch
--console-pty` exited 0 and the simulator's unified log names the process
ending without a status. **On the device, `devicectl` does report it, and the
status was 7** for both the debug build and the release `.ipa` (Step 6), so
exit status on iOS is proven there, not on the simulator.

### 3. `run --device` cannot pick between two paired iPhones with the same name

Not #68, and pre-existing. With this iPhone connected and an older one
(iPhone14,3, "unavailable") still paired under the same name, `run -p ios
--device` failed:

```text
Error: command failed (1): devicectl
multiple paired iOS devices found ('Elliot’s iPhone', 'Elliot’s iPhone') — pass one explicitly, e.g. `kivyforge run --device --destination 'NAME'`
```

The unavailable device is counted as a candidate, and the suggested fix (pass
the name) cannot separate two devices with one name. `--destination` with the
UDID worked. Candidates should probably exclude unavailable devices, and the
message should suggest the UDID.

`Built gui-demo-ios/build/DerivedData/Build/Products/Debug-iphonesimulator/gui-demo.app`.
The xcodebuild activity log has no `warning:` or `error:` lines. This was the
first compile of `kivyforge_main(..., entry_launcher, ...)` and
`_run_entry_launcher`.

`main.m` passes `ENTRY_POINT, ENTRY_LAUNCHER, APP_DIR, PYTHON_MAJOR_MINOR`.

`run -p ios --simulator` installed and launched the app. The console showed
`KF-GUI-DEMO: module=gui_demo.app greeting=relative import ok`, and the
screenshot (`~/kf-gui68/ios-gui-demo.png`) shows the button reading
`relative import ok` / `gui_demo.app:main()` / `tap to stop`.

The tap (a synthetic click on the device in Device Hub's window) reached the
button: `[Base] Leaving application in progress...`, then
`KF-GUI-DEMO: main() returning`. What the simulator did next is observation 1
above.

The non-zero path:

```text
$ SIMCTL_CHILD_KF_GUI_DEMO_PROBE=/tmp/probe-ios.txt \
    xcrun simctl launch --console-pty <udid> org.kivyforge.guidemo; echo "exit=$?"
```

## Step 6 — device and release `.ipa`: **pass**

Run after the steps above, once the phone was attached. The test app's
`team_id = ""` was left as is; the team came from `KIVYFORGE_TEAM_ID`.

**Debug build.** `build -p ios --device` compiled, linked and signed
(`Debug-iphoneos/gui-demo.app`, the same `main_config.h`). `run -p ios --device
--destination <udid>` (see observation 3 for why the UDID) installed and
launched it:

```text
Launched application with org.kivyforge.guidemo bundle identifier.
KF-GUI-DEMO: module=gui_demo.app greeting=relative import ok
[INFO   ] [Base        ] Start application main loop
```

The owner tapped the button: `Leaving application in progress...`, then
`KF-GUI-DEMO: main() returning`, and the app stayed on its last frame
(observation 1).

The non-zero path, with the probe pointed into the app's data container (the
path Kivy logs for its log file) and copied back afterwards:

```text
$ DEVICECTL_CHILD_KF_GUI_DEMO_PROBE=<container>/tmp/probe-device.txt \
    xcrun devicectl device process launch --device <udid> --terminate-existing \
    --console --json-output dev-launch.json org.kivyforge.guidemo
KF-GUI-DEMO: module=gui_demo.app greeting=relative import ok
KF-GUI-DEMO: main() returning
The app terminated with the exit code 7.
devicectl exit=7
$ xcrun devicectl device copy from ... --source tmp/probe-device.txt ...
gui_demo.app|relative import ok
```

`dev-launch.json` records `"exitCode" => 7`.

**Release `.ipa`.** `package -p ios --export-method development` exported
`dist/ios/gui-demo-0.1.0-development.ipa`. Its `app/` holds only `gui_demo/`
and `gui_demo-0.1.0.dist-info/`: no `_kivyforge_main`, since iOS compiles the
launcher into the binary. It holds `.py` sources, not `.pyc`: `package` warned
`not byte-compiling app sources: no final CPython 3.15 found (this project
ships 3.15.0b4)`, so this run does not exercise a bytecode-only iOS payload.
Installed with `devicectl device install app`, it logged the relative import,
and a tap again gave `main() returning`. With the probe set:

```text
KF-GUI-DEMO: module=gui_demo.app greeting=relative import ok
KF-GUI-DEMO: main() returning
The app terminated with the exit code 7.
devicectl exit=7
probe: gui_demo.app|relative import ok
```

The bare form was not re-run on the device; `hello-kivy`'s device pass is
the `ios-device` hardware check, last recorded 2026-09-30.
